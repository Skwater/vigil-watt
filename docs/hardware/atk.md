# ATK / VXE 2.4G 电量（接收器 VID_373B）

鼠标走 16 字节 op 帧，键盘走 VIA，同一个 VID 下按 usage page 分流。鼠标部分：协议出处是公开逆向项目 [0x44oge-ATK](https://github.com/ReformedDoge/0x44oge-ATK)，本项目在其基础上做了真机复核与补强。

- **设备**：ATK 烈空 F1 Pro Max、F1 V3 ULTIMATE+ 等同协议系列
- **VID**：`0x373B`（十进制 14139）。⚠ **不是**容易误抄的 `0x375B`
- **PID**：
  - 接收器：8K `0x101B`（产品名 `ATK Mouse 8K Dongle`）、1K `0x101A`、`0x1303`（产品名 `Wireless mouse 8k dongle-M`）
  - **鼠标本体（插充电线时枚举）**：**因型号而异**——F1 Pro Max = `0x1015`、F1 V3 ULTIMATE+ = `0x12A9`
    （本体上报的产品名即机型，如 `ATK F1 V3 ULTIMATE+`）。**因此本体不能靠 PID 白名单穷举**，
    插件改用"没有任何接收器在位时，剩下的就是本体"来判定，新型号自动支持。
- **本机验证**：F1 Pro Max 与 F1 V3 ULTIMATE+ 两台真机（电量 95% / 75%），与官方 ATK HUB 3.2.28 **共存实测无冲突**

## 1. 接口地图

| 接口 | 用途 |
|---|---|
| `MI_01&COL05`（usagePage `0xFF02` / usage `0x0002`，17B in-out） | **电量通道** |
| `MI_01&COL01`（`0xFF05`）、`COL03`（`0xFF03`）、`COL04`（`0xFF04`）、`COL06`（`0xFF06`） | 其它功能，非电量 |

认领条件：`VID == 0x373B` 且 **`UsagePage == 0xFF02`**（精确匹配电量口）。
⚠ 不能放宽成 `>= 0xFF00`：同一设备还有 FF03/FF04/FF05/FF06 等厂商口，放宽后基类会对每个口各跑一次探测，每个口都白白发一帧查询——违反 `safety.md` §3 规则 4 的限频要求。

### 1.1 长度判据

除usage page 外还要求**接口能收发 17 字节帧**（`in == 17 && out == 17`，对齐 PR #28 的 `IsSupportedInterface`）：

| 设备 | `in` | `out` | 来源 |
|---|---|---|---|
| F1 Pro Max 8K 接收器 `0x101B` | 17 | 17 | 本机实测 |
| F1 Pro Max 1K 接收器 `0x101A` | 17 | 17 | 本机实测 |
| F1 V3 ULTIMATE+ 8K-M 接收器 `0x1303` | 17 | 17 | 本机实测 |

- **接收器**用严格判据 `in == 17 && out == 17`（三个 PID 实测一致）。
- **有线本体**（插充电线时才枚举出来，PID 随型号变）只要求"容得下"（`in >= 17 && out >= 17`）——
  本体的接口长度尚未实测，写死 `== 17` 会在实测出别的长度时把本体误杀。

⚠ **长度判据放松就会被回显帧骗到**：同一接收器上 `0xFF60`（VIA）等其它通道会把请求原样回显，
回显帧的校验和是旧值——只有"帧长判据 + 校验和"同时成立才挡得住（PR #28 的实测结论）。

## 2. 帧格式（17 字节，report ID `0x08`）

请求：

```
08 04 00×14 49
```

校验算法（0x44oge 的 `calculateAtkChecksum`）：`尾字节 = (0x55 − 前 16 字节之和) & 0xFF`，本例即 `0x49`。
（"前 16 字节" = report ID + op 帧的前 15 字节；op 帧口径写法见下方说明。）
帧构造见 `AtkCodec.BuildQuery`。

> **帧长两种记法，同一协议**：上面写的是"线上 17 字节（含 report ID）"。
> 另一种记法是"op 帧 16 字节（不含 report ID）"，校验写成 `chk = (0x4D − op 帧前 15 字节之和) & 0xFF`。
> 两式**完全等价**（`0x4D = 0x55 − 0x08`）：已对本机抓到的 20 帧逐帧验算，两种口径全部通过。
> PR #28 用的是 op 帧记法，本 PR 用的是含 report ID 的线上记法——合并时按任一种统一即可，
> **不要留两套帧长判据**。

响应：

```
08 04 <b2> <b3> <b4> <b5> <电量%> <充电> <电压mV大端16位> … <校验>
```

| 偏移 | 含义 | 实测样本 |
|---|---|---|
| `[6]` | 电量百分比 | `0x5F` = 95%、`0x64` = 100% |
| `[7]` | 充电 / 有线标志 | **`0x00` = 放电（无线）；`0x01` = 充电（有线）** |
| `[8..9]` | 电池电压（大端 16 位） | `0x0FFC` ≈ 4092 mV、`0x1061` ≈ 4193 mV |

实测原始帧（**均为本机抓包**，见 §3.1）：

```
无线·放电 95%   08 04 00 00 00 02 5F 00 10 01 00 00 00 00 00 00 D7
无线·放电 95%   08 04 00 00 00 02 5F 00 0F FC 00 00 00 00 00 00 DD
有线·充电 95%   08 04 00 00 00 02 5F 01 10 61 00 00 00 00 00 00 76
有线·充电 95%   08 04 00 00 00 02 5F 01 10 5D 00 00 00 00 00 00 7A
无线·放电 100%  08 04 00 00 00 02 64 00 10 1E 00 00 00 00 00 00 B5
```

几点值得注意：

- **校验算法得到独立验证**：上列 5 帧的尾字节全部符合 `(0x55 − 前 16 字节之和) & 0xFF`。
  ⚠ 早期文档写作"前 15 字节"，漏算了 `[15]` 那一字节；本批样本的 `[15]` 恰好恒为 `0x00`，
  所以两种写法在本批抓包上结果一致——但口径必须写准，合并成一份 codec 时才对得上。
- **响应帧必须过校验和才采信**（`AtkCodec.ChecksumValid`）：固件会在同一设备上混发普通鼠标报文与
  厂商私有集合帧，只看"命令字 + 电量范围"会把非电量帧读成假读数；校验和是当前唯一能挡住这类帧的判据。
- **设备会把请求原样回显**：回显帧的校验和是**对的**、但电量位是 `0`，靠电量下界（`≤1` 视为休眠占位）挡住。
- **同一设备上确实混发非电量帧**（2026-10-24 实机复验时抓到）：
  `08 03 00 00 00 01 01 CB B3 8D 00 00 00 00 00 00 3D` —— 命令字是 `0x03`（不是 `0x04`），
  在同一次读的队列里紧跟着电量帧出现。这条帧命令字判据能挡住，但**校验和是独立于命令字的第二道防线**：
  凡是"命令字合法 + 电量位落在 2–100、但校验和对不上"的帧，旧实现会直接读成假读数，新实现一律拒绝。
- **`[8..9]` 是实时电压，不是常量**：同一状态下会在几 mV 内抖动（4092↔4097、4126↔4130）。
- **充电时电压高于放电时**：充电 4189~4193 mV vs 放电 4092~4097 mV，符合物理。
- **`[7]` 是可靠的充电判据**：`0x00` / `0x01` 在各自状态下连采多条均稳定，未见抖动。

## 2.1 三种接收器的对照测试

ATK 同族鼠标标配多个接收器（一只鼠标可切 1K / 8K 无线模式）。**三个接收器都认同一条查询帧
`08 04 00×14 49`，响应结构完全一致**：

| | 8K `0x101B` | 1K `0x101A` | 8K `0x1303` |
|---|---|---|---|
| HID 产品名 | `ATK Mouse 8K Dongle` | （1K dongle） | `Wireless mouse 8k dongle-M` |
| 电量接口 | `MI_01&COL05` / `0xFF02` | **相同** | **相同** |
| 输出 / 输入报告长度 | 17 / 17 | **17 / 17** | **17 / 17** |
| Feature 报告长度 | 0 | **0** | **0** |
| 查询帧 | `08 04 …49` | **同一条** | **同一条** |
| 响应字节数 | 17 | **17** | **17** |
| `[6]`电量 / `[7]`充电位 / `[8..9]`电压 / `[16]`校验 | ✅ | **完全一致** | **完全一致** |
| `MI_00` | HID-compliant mouse | HID Keyboard Device | HID-compliant mouse |
| `MI_02` | USB Keyboard Device | HID-compliant mouse | HID Keyboard Device |
| 接口总数 | 10（含 `MI_01&COL08`） | 9 | 13（`MI_01` 多 COL07/COL08） |

`0x1303` 实测响应（连采 5 条全部应答、校验全部通过，电量 75%）：

```
08 04 00 00 00 02 4B 00 10 3A 00 00 00 00 00 00 B2    ← 第 1~3 条
08 04 00 00 00 02 4B 00 10 35 00 00 00 00 00 00 B7    ← 第 4~5 条
```

1K 实测响应（连采 5 条全部应答、校验全部通过，电量 100%）：

```
08 04 00 00 00 02 64 00 10 22 00 00 00 00 00 00 B1    ← 第 1~4 条
08 04 00 00 00 02 64 00 10 1E 00 00 00 00 00 00 B5    ← 第 5 条
```

差别只在**接口角色**上（枚举顺序不同，内容一一对应）：`101A` 的 `MI_00` 是键盘口、`MI_02` 是鼠标口，
**与 8K 正好互换**；`101B` 多一个 `MI_01&COL08`。

⚠ **踩过的坑**：前两次测 `0x101A` / `0x1303` 时鼠标电源是关的，5 次全部无应答，差点误判成
"这些接收器不支持这条帧"。**排查顺序应是：先确认鼠标已上电并与当前接收器配对，再谈协议差异**——
休眠/关机的表现同样是"不回帧"（见 §3）。

## 3. 休眠 / 关机时的行为

**实测结论（2026-10-23 本机抓包，两轮独立复核）**：鼠标闲置后，dongle 对电量查询帧**完全不回应**——
不是回 0、不是回旧值，而是**没有任何 `08 04` 帧返回**（每种状态连采 3 次，每次等 1.2s 均无响应）。
**关闭鼠标电源开关后同样不回**。

```
[第1轮] 闲置 20 分钟后 · 3 次查询 → 全部无响应（1.2s 内没读到 08 04 帧）
[第2轮] 闲置 10 分钟后 · 3 次查询 → 全部无响应
[第1轮] 关闭电源开关后 · 3 次查询 → 全部无响应
[第2轮] 关闭电源开关后 · 3 次查询 → 全部无响应
```

注意：dongle 本身**始终在位**——`MI_01&COL05` / usagePage `0xFF02` 接口照常被 Windows 枚举出来，
只是不会替一只睡着的（或断电的）鼠标回帧。**休眠与关机的表现完全一致**，无法区分这两者。

这一点对实现的影响：

- 读不到帧 → 插件按"查询失败"记账 → 连续 3 次触发**熔断停写 + 递增退避**（基类机制）。
  日志里可见完整循环：`连续 3 次查询失败，熔断停写` → `停写退避期满（30 秒），恢复查询` → 再失败 → 退避 60 秒…
- 退避是**必需**的：鼠标休眠是常态，固定的长退避会把"唤醒后恢复读取"一起挡死
  （`docs/hardware/safety.md` §3 规则 3 的由来，正是同类教训）。
- 唤醒后第一次查询成功即清零失败计数、解除熔断。

因此**不需要**为休眠态专门解析什么——插件读不到帧就不更新读数，界面保持"最后已知读数 + 离线标记"。

⚠ 此前曾按参考实现的推断写成"休眠时仍会回应一帧、电量字节为 0"，**已被实测证伪**：本机休眠时是**完全不回**。
代码里"拒绝电量 ≤ 1"的防护仍保留（防止其它场景读到 0%），但它不是针对本机休眠行为的。

### 3.1 原始帧样本

| 轮次 | 场景 | 原始 17 字节 hex | `[7]` | 电压 |

| 1 | 无线 · 放电 | `08 04 00 00 00 02 5F 00 0F FC 00 00 00 00 00 00 DD` | `0x00` | 4092 mV |

几点值得注意：

- **两轮独立复核结论一致**：`[7]` 跨轮次、跨状态恒为 `0x00`（放电）/ `0x01`（充电）；
  充电态连采 5 条全为 `0x01`，未见抖动。
- **满电时 `[7]` 仍是 `0x00`**——它表达的是"**正在充电**"，不是"**插着线**"
  （满电那会儿鼠标插的是接收器，无线）。
- **`[6]` 与 `[7]` 相互独立**：满电 100% 配 `0x00`、充电 95% 配 `0x01`，两个字段各管各的。
- **校验字节全部符合** `(0x55 − 前 15 字节之和) & 0xFF`（两轮共 11 帧逐帧核对）。
- **`[8..9]` 是实时电压**：同一状态下有几 mV 抖动（放电 4092~4138、充电 4189~4197）。

回归单测 `AtkCodecTests.A3` / `A4` 用的是**按协议构造**的边界样本（用于锁住"不校验电量下界就会读出 0%"
这一行为），不代表抓包证据。

### 3.2 有线模式的枚举行为

**Windows 会把插线充电时的鼠标本体枚举成另一台设备实例**（PID 与接收器不同），
且**本体 PID 因型号而异**：

| | 接收器 | 插线时的本体（F1 Pro Max） | 插线时的本体（F1 V3 ULTIMATE+） |
|---|---|---|---|
| PID | `0x101B`（8K）/ `0x101A`（1K）/ `0x1303`（8K） | `0x1015` | **`0x12A9`** |
| HID 产品名 | `ATK Mouse 8K Dongle` / `Wireless mouse 8k dongle-M` | `ATK F1 PRO MAX` | **`ATK F1 V3 ULTIMATE+`** |
| 电量接口 | `MI_01&COL05`，usagePage `0xFF02`，17B in-out | **同样是 `MI_01&COL05` / `0xFF02`** | **同样是 `MI_01&COL05` / `0xFF02`** |
| 电量接口路径实例号 | `8&A2C29E2&0&0004` | `8&2B7F60F&0&0004` | `8&1D6F4258&0&0004` |
| 键盘口实例号 | `MI_02` `8&3296D7AB` | `MI_02` `8&97FFED` | `MI_02` `8&A3F261A` |
| 接口总数 | 10（多一个 `MI_01&COL08` / `0x0001`） | 9 | 10 |

接口结构一一对应：本体与接收器的 **COL01~COL07 完全对应**（`FF05` / `FF03` /
`000C` / `0001` / `FF04` / `FF06`），只有接收器多一个 `COL08`。

两端读到的**电量一致**（同为 95%），差别只在 `[7]` 充电标志（本体 `0x01`，
接收器 `0x00`）——因为插线时接收器已经不在位，读到的是鼠标本体自己的电池状态。

F1 V3 ULTIMATE+ 插线时的实测响应（`[7]`=`0x01`，与 F1 Pro Max 一致）：

```
08 04 00 00 00 02 5F 01 10 E2 00 00 00 00 00 00 F5    电量95%  充电位 0x01  4322mV  校验OK
```

⚠ **本体 PID 不可穷举**（`0x1015` / `0x12A9` … 随型号变），所以插件**不靠 PID 白名单认本体**，
而是"没有任何接收器在位时，剩下的 0xFF02 接口就是本体"——新型号自动支持，无需改代码。

插件据此把两个接口归一到同一条设备记录（见 §4）。

## 4. 设备 ID 归一：按「配对组」，一只鼠标一条

同一台鼠标的**接收器**与**插充电线时枚举出的本体**是同一台设备（充电时通常要拔掉接收器腾 USB 口，
两个接口会先后出现）。若按接口路径生成 ID，UI 上就会多出一台"设备"，且拔线后那条记录残留。

但**不能**简单地按「厂商 + VID」归一——那样同机接两台 ATK 鼠标（F1 Pro Max 与 F1 V3 ULTIMATE+）
会共用一条记录、读数串台。

该鼠标的 HID 描述符**序列号为空**，容器 ID 也不同，**硬件层没有可自动配对的标识**，
只能按真机实测出的配对表归组：

| 组 | 接收器 PID | 本体 PID（有线模式） | 机型 |
|---|---|---|---|
| `promax` | `0x101B`（8K）、`0x101A`（1K） | `0x1015` | ATK 烈空 F1 Pro Max |
| `v3` | `0x1303`（8K-M） | `0x12A9` | ATK F1 V3 ULTIMATE+ |

⚠ 同一只鼠标可配**多个接收器**（F1 Pro Max 标配 1K 与 8K 两套），它们属于**同一组**——
同机插两个接收器也只显示一条设备记录。

- 插件覆盖基类的 `IdFor`，按组生成 `atk-promax` / `atk-v3`：**同组共用一个 ID，不同鼠标各自一条**。
- **未登记的 PID 交回基类默认（路径哈希）**，即等同上游行为——宁可充电时多一条，
  也不能把两台不同的鼠标并成一条。
- 认领时**同组的接收器优先**（常规无线使用、名称稳定）；只有**本组**的接收器不在位时，
  才认领该组的有线本体——此时能读到充电状态。
  ⚠ 必须按本组判，不能按全局有没有接收器在位：同机接两台 ATK 鼠标时，
  另一台的接收器在位会把本台的本体误判掉（2026-10-23 实机复现：F1 V3 插线后本体不认领）。

⚠ 配对表是实测结论，新增型号需要补一行；补之前该型号会退化为上游默认行为（可显示，但充电时多一条）。

### 4.2 换插充电线时另一台设备短暂离线（已修）

Windows 在 USB 重新枚举 HID 设备时，旧句柄会失效、读帧失败。若把这种句柄失效当成设备故障
计入失败计数，会连续触发熔断，让**另一台**鼠标假离线 30~60 秒（退避恢复）。

插件据此区分两类失败：**写帧失败 = 句柄已失效**（设备被拔出或重枚举，不计失败，基类下一轮
扫描会移除旧记录并重新认领）；**读帧失败 = 设备在位但不回帧**（鼠标休眠，该熔断）。

### 4.1 显示名从哪来

| 场景 | 显示名 | 来源 |
|---|---|---|
| 无线（接收器在位） | `Wireless mouse 8k dongle-M`（或 `ATK Mouse 8K Dongle`） | 接收器上报的 HID 产品字符串 |
| 插线充电（本体在位） | `ATK F1 V3 ULTIMATE+` | 本体上报的 HID 产品字符串（即机型） |

**接收器上报的是通用名，不含机型**；其余厂商口（FF03/FF04/FF05/FF06）被动读 1.5 秒**零帧**，
只在被查询时应答——所以**型号信息只有插线时本体枚举出来才能拿到**。

插件的处理：本体被枚举过一次后，把它的产品名**按归一组**记住（进程内缓存），之后显示名就用它。
多只鼠标各记各的，不会互相覆盖。进程重启后需要再插一次线才能恢复；也可以在设置页用
**设备自定义**功能固定改名。

## 5. 写入边界

- 只会写**一条**固定查询帧 `08 04 …49`，不发任何其它命令
- 该设备独占 `WriteFile` 不可用（0x44oge 源码注释 "Only one that works"），故 `WriteOutput` 失败时回落
  `HidD_SetOutputReport`（非独占、经 HID 类驱动路由，可与 ATK HUB 的 WebHID 驱动同开）
- **会写帧 → 插件默认关闭**（`docs/hardware/safety.md` R1），用户在设置页自行开启
- 连续 3 次查询失败 → 熔断停写 + 递增退避（基类机制），鼠标休眠时的常见表现

## 7. 键盘：VIA 读键盘值（page `0xFF60`）

ATK 键盘（A98 Pro，`373B:1152`）走标准 VIA 之上加的一层 `customId` 扩展：

```
[0] 0x00（前导）  [1] 0x02（id_get_keyboard_value）  [2] 0x96（customId）  [3] 0x24（battery）
```

响应实测 `00 02 96 24 64 01 …`：

| 偏移 | 含义 |
|---|---|
| `[0]` | 前导 `0x00`（不是 report ID，解析时跳过） |
| `[1]` | `0x02` 命令回显 |
| `[2]` | `0x96` customId |
| `[3]` | `0x24` 电量键 |
| `[4]` | **电量百分比**（样本 `0x64` = 100） |
| `[5]` | 充电标志：非 0 = 充电中 |

- 解析要求 `[1..3]` 三个命令字节全部对上，带/不带前导 `0x00` 两种偏移都试（`AtkViaCodec.TryParse`）。
- 接口判据：同 VID、`usagePage 0xFF60`、进出等长且 ≥5 字节、report ID 为 `0x00` 或缺省。
- **不要用 op 帧读键盘**：`0xFF60` 接口对 op 帧只回显请求，`data[0]` 恒为 `0x29`、校验和不重算，读出来必然是 41%——本项目踩过的坑。
- 官方客户端在充电时不显示百分比（`power = 0 === batteryCharge ? batteryLevel : undefined`）；本插件照读数显示并标"充电中"。

**型号表**（只按 PID 查，产品串不能当判据：`11E4` 的产品串是 `ATK F1 ULTIMATE 2.0`，不含 "mouse"）：

| PID | 型号 | 链路 |
|---|---|---|
| `0x1152` | ATK A98 Pro | VIA 键盘 |
| `0x11D9` / `0x11E4` | ATK F1 Ultimate 2.0 | op 帧鼠标 |

其余 ATK PID 默认按鼠标算，型号名退回产品串。键盘与鼠标共用一个 `Atk` 开关（品牌级），设置页一行。

## 8. VXE R1 Nearlink（373B:10C9，2026-10-27 本机验证）

蓝牙连接时软件界面及有线 USB 产品串均显示 **VXE R1 Nearlink**，本适配统一采用此名称；接收器 USB/HID 产品串为 `NK mouse NANO dongle`。本机官方 ATK HUB 的 `resources/main/app.asar` 内，`static/filter-B6RHekbD.js` 登记了 `vendorId:14139, productId:4297`（即 `373B:10C9`）接收器，电量命令 `GetBatteryLevel=4`、16 字节 op 帧、report ID `8` 与现有 `AtkCodec` 相同。仅核对读取路径，没有执行官方脚本。

### 8.1 接口与认领

| 集合 | UsagePage / Usage | IN / OUT / Feature | 处理 |
|---|---|---|---|
| `MI_01&COL04` | `FF02 / 0002` | `20 / 20 / 0` | 排除，不发送查询 |
| `MI_01&COL05` | `FF02 / 0002` | `17 / 17 / 0` | 唯一电量接口 |
| `MI_01&COL06` | `FF04 / 0002` | `0 / 0 / 8` | 排除 |
| `MI_02` | `0001 / 0002` | `8 / 0 / 0` | 普通鼠标输入，排除 |

原代码把未知 PID 当作有线本体，而在位接收器缓存包含设备自身，导致 `10C9` 被自身排除。将它加入接收器列表后，直接走严格的 `17 / 17` 判据，同时排除同页的 20 字节集合。显示名映射为 `VXE R1 Nearlink`；共用原有 `Atk` 品牌开关，默认关闭。

### 8.2 实测证据与边界

两个 `FF02` 集合各被动监听 15 秒，均为 0 帧；随后只向 17 字节接口发送一次已有电量查询：

```text
TX 08 04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 49
RX 08 04 00 00 00 02 3C 00 0E F2 00 00 00 00 00 00 0B
```

校验和通过，`[6]=0x3C` 对应 **60%**，`[7]=0` 对应协议定义的未充电，`[8..9]=0x0EF2` 对应 **3826 mV**。该原始帧加入 `AtkCodecTests`，接口筛选与名称由 `AtkReceiverTests` 回归验证。

无线与有线充电均已读取；尚未核对官方界面的电量、关机/休眠、同一长驻进程的热切换及重插行为。没有修改 DPI、回报率、配对或固件。

### 8.3 有线充电与接口接管

用户插线充电后新增本体 `373B:10C7`，产品串 `VXE R1 Nearlink`，同样有 20 字节与 17 字节两个 `FF02` 集合。向接收器 `10C9` 查询未收到应答；向本体的 `MI_01&COL05`（17 字节）发送相同查询，得到：

```text
RX 08 04 00 00 00 02 50 01 0F 82 00 00 00 00 00 00 65
```

校验通过：电量 **80%**，充电位 `[7]=1`，电压 **3970 mV**。修改后的真实插件随后读取到 **85%、Charging、在线**，设备列表仅一条；两次读取之间鼠标仍在充电。

`SkipPathsForThisPass` 在有效的 `10C7` 电量接口在位时释放并跳过 `10C9` 接收器，避免查询静默通道；本体的同页 20 字节集合仍被严格排除。两种连接方式归入 `r1nk` 组，统一设备 ID `atk:atk-r1nk` 与名称 `VXE R1 Nearlink`。设备 ID 采用现有配对组机制；从早期仅无线测试版的路径哈希 ID 升级时，旧历史不会自动迁移。同机多只此型号仍会共用该组 ID，属于既有 CR-99 的限制，未在本次扩展为逐物理设备配对。拔线后按扫描结果重新允许接收器，重新扫描读取的实测见 §8.4。
